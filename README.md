# planning

기획 공부·아이데이션 툴의 **사례 DB**입니다. 지금은 DB만 있고, 툴 화면은 보류 중입니다.

방법론: **WHAT**(무슨 문제를 풀 것인가) → **가설**(최대한 많이) → **Why not yet**(왜 지금까지 아무도 안 했나?) → 해결

Why not yet은 두 가지 일을 합니다.
1. 뻔하거나 불가능한 아이디어를 제거한다 → `obvious`(뻔함), `impossible`(불가능): 탈락
2. 주목하지 않던 아이디어가 빛나는 아이디어였음을 깨닫게 한다 → `blindspot`(통념의 맹점), `timing`(타이밍): 생존

## 규모
- 사례 **305개** (실제 244 · 실패 23 · 연습 38), 가설 **1098개** (사례당 3개 이상)
- 출처 링크 확인(✓) 31개

실제·실패 사례는 학습용으로 단순화한 재구성입니다. ✓가 없는 실제·실패 사례는 `source`에 적은 책·기사·일반적으로 알려진 내용을 바탕으로 해서, 인용하기 전에 확인이 필요합니다. 공항 수하물 사례는 공항·연도가 확인되지 않았다는 지적이 있어 '전해지는 이야기'로 다룹니다.

## 파일
| 파일 | 내용 |
|---|---|
| `db/cases.json` | 완성된 DB (빌드 결과, 직접 고치지 않음) |
| `db/base.json` | 처음 30개 사례 (JSON으로 작성) |
| `db/src/*.txt` | 분야별 사례 원본 (간단 작성 형식) · `9x-*.txt`는 가설 보강과 출처 링크 |
| `tools/build_db.py` | `db/base.json` + `db/src/*.txt` → `db/cases.json` |
| `tools/check_db.mjs` | 형식 검사 |

```bash
python3 tools/build_db.py
```
```bash
node tools/check_db.mjs
```

## 작성 형식 (`db/src/*.txt`)
```
# id | 제목 | 분야 | real·failure·practice | 출처
S: 상황
X: 현상(겉으로 보이는 문제)
P: 다시 정의한 문제
- B cu | 가설 | Why not yet 답 | 판정 이유
= 해결
L: 배울 점
R: https://출처 (있으면 verified)
```
- 판정: `O` 뻔함 · `I` 불가능 · `B` 통념의 맹점 · `T` 타이밍
- 관점: `cu` 고객 · `ti` 시점 · `pr` 가격 · `ch` 채널 · `co` 경쟁 · `cn` 제약 · `be` 통념
- 기존 사례에 가설·출처 덧붙이기: `@ id` 다음 줄에 `- …` 또는 `R: …`
- 실패 사례는 생존 가설이 없어도 됩니다 (Why not yet이 경고했는데 무시한 경우).
